# Email command interface (`-request`) and owner forwarding

Subscribers and non-subscribers administer a list by email through the `listname-request@domain` address, Mailman-style: one command per line in the message body, case-insensitive, blank and quoted (reply) lines ignored. Commands act on the sender's own subscription with the From address as identity, matching the existing model (no passwords). The command set: `help`, `which` (all of the sender's subscriptions across every list/domain), `info` (list description, type, policy, moderation, posting rules), `set regular|digest|nomail` (delivery preference), `re-enable` (a Disabled subscription returns directly to Active; the bounce count is kept), `unsubscribe` (same effect as the `-unsubscribe` address), `who` (member roster; restricted to Owners and Moderators only), and `contact` (forwards free text to the list's Owners). `contact` terminates command parsing: everything after it in the body is the message. Replies are one combined plain-text email per request, From the list address, envelope sender VERP-encoded, Reply-To the `-request` address so replying continues the conversation; every command gets a result line — unknown, malformed, and unauthorized commands are never silent. The `listname-owner@domain` address is now live too: it forwards the whole message to all Owners, deduplicated, sender excluded if an Owner, Reply-To set to the sender so an Owner can reply directly. We chose email-only (no password machinery) because the system is passwordless by design, per-list addressing because every member knows their list's address, and direct action without a confirm step because the existing `-unsubscribe` address already acts on From-address identity.
