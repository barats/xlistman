# Web server administration: the Administrator role

Phase 7 brings server-level administration onto the web through a new instance-wide **Administrator** privilege — a Subscriber designated via the CLI (`admin add|remove|list`, the first by the server operator) who can create domains and lists, manage other Administrators, delete lists, and change ListType, from a server-admin area in the web console visible only to Administrators. This supersedes ADR 0005's CLI-only stance for these operations. ADR 0005 rejected web server administration because it "would require a separate admin authentication mechanism"; that objection no longer holds now that the web UI has working Magic Link Subscriber auth (ADR 0012) — an Administrator is simply a Subscriber with an instance-wide flag, authorized on each request like a List Role, so no second authentication system is introduced. CLI commands for the same operations are retained (list create/delete, new list type and admin commands), sharing the same store functions as the web so the two surfaces cannot drift. List creation mirrors the CLI: the creating Administrator is the default first Owner, overridable to any known Subscriber, so a list is never accidentally ownerless. List deletion is a hard delete: the list plus its settings, archive, held messages, subscriptions, roles, and queue entries are removed in one transaction — fixing the pre-existing bug where `DeleteList` removed only the List row and orphaned all related data (no foreign keys exist in the schema) — and the web requires typing the full list address to confirm, with the deletion logged server-side. ListType changes are reversible and carried with a warning dialog that states the posting-policy consequence ("subscribers will stop being able to post" / "all subscribers will now be able to post").

**Considered Options**:
- Open self-service list creation by any verified Subscriber — rejected: lets any signed-in address spin up lists that send mail, opening an abuse surface that contradicts the trusted-identity model where Subscribers are verified by double opt-in or a trusted actor's action.
- Hybrid self-service creation with Administrator approval of held lists — rejected: would introduce a held state for Lists that does not exist today and add approval plumbing, for little gain given creation is already gated to trusted Administrators.
- Soft delete with a Retired list status — rejected: the destructive intent is explicit and a proper hard-delete cascade with address confirmation satisfies it; a Retired state would keep deleted names occupied and require a purge story. (It remains a viable future option if archive retention is ever wanted.)
- Keeping list deletion and ListType changes CLI-only — rejected: the goal is fully self-service provisioning; the CLI is retained for scripting, and the operator's shell gate is replaced by the typed-address confirmation for the one irreversible action.
