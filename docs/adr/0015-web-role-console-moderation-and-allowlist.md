# Web role console for moderation and the newsletter allowlist

Phase 3 shipped the SvelteKit web UI (ADR 0007), which makes the rationale ADR 0010 gave for email+CLI-only moderation — "the web UI is deferred" — stale. We now add a web role console: a List Role (Owner | Moderator | Designated Sender) is a privilege a Subscriber holds on a List beyond subscribing, and the console surfaces every list where the signed-in Subscriber holds a role. Owners and Moderators act on Held Messages with the same Moderation Actions (Approve, Reject, Discard) as the email and CLI paths, through one shared function so the three paths cannot drift. Authorization is the existing Magic Link Session plus a server-side role check per list, and web actions address Held Messages by raw ID — unlike email URLs, which keep opaque per-message tokens (ADR 0010), because the web server verifies the role on every request. Owners also manage a Newsletter list's Designated Sender allowlist from the console, and server administrators via the CLI (ADR 0005). Designation is Subscriber-first: only a known (verified) Subscriber can be designated. A Designated Sender gains posting rights only, not Archive access, which remains members-only. The role console supersedes ADR 0010's deferred-web rationale; the email and CLI paths remain.

**Considered Options**:
- Web links reusing the opaque per-message token (like email) instead of session + role check — rejected: an authenticated session already proves identity and role, tokens would make URLs unguessable-but-unbookmarkable for no added security.
- Implicitly creating a bare Subscriber when a sender is designated — rejected: it would let an unverified address post to a Newsletter list, eroding the verified-address guarantee that double opt-in enforces.
- Granting Designated Senders Archive access — rejected: posting rights and reading rights stay separate, keeping archives members-only.
