# Single-instance with multi-instance-ready design

xListman runs as a single process for v1. One daemon handles LMTP inbound, HTTP web UI/API, and all background workers (queue processing, digest generation, bounce tracking, held message expiry) using goroutines for concurrency. SQLite (single-writer) is the default database. We chose single-instance because mailing list workloads are I/O-bound (waiting on the MTA), not CPU-bound - a single Go process handles thousands of lists and millions of subscribers. The real bottleneck is the MTA, not xListman.

However, the system is designed to be multi-instance-safe by using database-level atomic operations instead of in-memory state everywhere coordination matters: the outbound queue uses an atomic claim pattern (`UPDATE ... SET claimed_at = now() WHERE id = ? AND claimed_at IS NULL`), rate limiting counters are stored in the database, digest generation uses atomic timestamp updates, and sessions are database-backed. This prevents race conditions within a single instance and means multi-instance is a deployment change (switch to PostgreSQL, deploy multiple instances behind a load balancer) rather than a code change. The atomic operations work with both SQLite (single-instance, serializes writes) and PostgreSQL (multi-instance, concurrent writes).
